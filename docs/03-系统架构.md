# 系统架构

## 1. 总体架构

```text
┌─────────────────────────────────────────────┐
│                 微信生态                     │
│  消费者小程序           商户小程序            │
└────────────────┬────────────────────────────┘
                 │ HTTPS
                 ↓
┌─────────────────────────────────────────────┐
│               API Gateway                   │
│        登录鉴权｜限流｜日志｜签名              │
└────────────────┬────────────────────────────┘
                 │
         业务服务层（一期可单体，后期可拆）
├── user-service
├── merchant-service
├── ticket-service
├── coupon-service
├── blindbox-service
├── point-service
├── checkin-service
├── ai-service
├── risk-service
├── message-service
├── statistics-service
└── third-platform-service
                 │
         基础设施
├── MySQL
├── Redis
├── RabbitMQ
├── OSS / MinIO
├── Elasticsearch（可选）
└── 大模型 / OCR
```

## 2. 一期与二期拆分建议

### 一期（推荐）

单体/模块化单体：

```text
api-server
 ├ modules/user
 ├ modules/merchant
 ├ modules/ticket
 ├ modules/coupon
 ├ modules/blindbox
 ├ modules/point
 ├ modules/checkin
 ├ modules/admin
 └ workers: ocr / ai / expire / statistics
```

### 二期

按流量与团队规模拆服务，优先拆：

1. `ai-service`
2. `ticket-service`
3. `coupon-service`
4. `statistics-service`

## 3. AI 审核中心

```text
上传票据
  ↓
OCR 提取字段
  ↓
票据分类
  ↓
P 图 / 截图检测
  ↓
信息完整性校验
  ↓
重复检测
  ↓
风险评分
  ↓
自动通过 / 人工 / 拒绝
```

### 风险评分（100 分）

| 维度 | 分值 |
| --- | ---: |
| OCR 完整度 | 25 |
| 图像真实性 | 25 |
| 商户可信度 | 15 |
| 时间合理性 | 10 |
| 重复票据 | 15 |
| 用户风险 | 10 |

| 分数 | 动作 |
| --- | --- |
| ≥ 85 | 自动通过 |
| 60 ~ 84 | 人工审核 |
| < 60 | 自动拒绝 |

- `verify(code)`
- `consume(code, merchantContext)`

## 5. 数据存储分工

| 存储 | 用途 |
| --- | --- |
| MySQL | 业务主数据、流水、配置 |
| Redis | Token、库存、幂等锁、排行榜、限流 |
| MQ | OCR/AI/发券/统计异步解耦 |
| OSS | 票根原图、打卡照片、Banner |
| ES（可选） | 后台检索与运营分析 |

## 6. 安全边界

1. 小程序登录走微信 `code2session`，服务端签发 JWT/Session。
2. 商户端与管理端权限隔离。
3. 核销接口必须校验商户门店归属。
4. 管理端操作写审计日志。
5. AI Key、第三方密钥走配置中心/环境变量。
